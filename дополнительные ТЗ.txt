ДОПОЛНИТЕЛЬНЫЕ ТЕХНИЧЕСКИЕ ЗАДАНИЯ (ФАЗА QA)

Статус: Запуск фазы QA и стабилизации
Срок: от 3 дней до 4 недель
Цель: Внедрение дополнительных модулей для расширения функциональности агента, тестирования в реальных условиях и подготовки к продакшн-развёртыванию.

Все изменения в этом документе направлены на:
1. Расширение возможностей агента (криптография, локальный парсер, дашборд).
2. Создание инструментов для мониторинга и отладки.
3. Подготовку инфраструктуры для обратной интеграции.
4. Проведение QA-тестирования в условиях, приближенных к боевым.

Критерии завершения фазы QA:
- Все три ТЗ реализованы и покрыты тестами.
- Дашборд запущен и отображает актуальные метрики.
- Локальный парсер успешно читает файлы из разрешённых папок.
- CryptoProvider интегрирован в BackupManager.
- Обратная интеграция Streamlit → Agent работает (отправка команд агенту).
- Проведено ручное тестирование основных сценариев.
- Обновлена документация.

ТЗ-ДОП-1: Интерфейс CryptoProvider (заглушка)

Цель: Создать абстрактный слой для будущего шифрования без реализации криптографии на текущем этапе.

Требования:
Создать модуль core/crypto.py.
Определить абстрактный класс CryptoProvider с методами:
  encrypt(data: bytes) -> bytes
  decrypt(data: bytes) -> bytes
  rotate_key() (заглушка, пока pass).
Реализовать класс NoOpCryptoProvider, который возвращает данные без изменений.
Внедрить провайдера в BackupManager через конструктор (параметр crypto_provider).
В тестах использовать MockCryptoProvider (например, добавляющий префикс) для проверки цепочки вызовов.
Криптография (Fernet/PBKDF2) откладывается до востребования (YAGNI).

Интеграция: BackupManager использует crypto_provider.encrypt() при записи и decrypt() при чтении.

QA-фокус: Проверить, что бэкапы создаются корректно с разными провайдерами, что данные не теряются при ротации (пока заглушка), что интерфейс готов к будущей реализации.

ТЗ-ДОП-2: Плагин Local Reader (локальный парсер)

Цель: Обеспечить чтение локальных файлов из разрешённых папок (белый список) с поддержкой основных форматов.

Требования:
Создать плагин plugins/local_reader/tool.py с классом LocalReaderTool, наследующим BaseTool.
Плагин принимает параметры:
  path: str — путь к файлу (относительно корня проекта или абсолютный, но проверяется).
  parser: str = "auto" — тип парсера (csv, json, txt, md, xlsx).

Безопасность:
  Разрешены только папки data/ и reports/ (и их подпапки).
  Проверка через os.path.abspath и startswith — запрет выхода за пределы (path traversal).
  При нарушении возвращать структурированную ошибку (через make_error).

Форматы:
  csv → возвращать список словарей (первая строка — заголовки).
  json → десериализовать и вернуть объект.
  txt, md → вернуть содержимое как текст.
  xlsx (опционально, если установлена openpyxl) → прочитать первую страницу как список словарей.
  auto → определять по расширению.

Возвращаемая структура: {"status": "success", "source": "local", "content": ..., "rows_count": ..., "file_path": ...}.

Тесты: проверка успешного чтения, ошибки при недоступном файле, защита от path-traversal.

Интеграция: Плагин автоматически обнаруживается PluginRegistry. Может вызываться через ReAct-цикл по команде пользователя (например, «прочитай reports/sales.csv») или напрямую из дашборда (через текстовый запрос агенту).

QA-фокус: Протестировать чтение различных форматов, проверить защиту от path traversal, убедиться что плагин корректно интегрируется в ReAct-цикл и вызывается через естественный язык.

ТЗ-ДОП-3: Интерактивный дашборд (Streamlit)

Цель: Создать графический интерфейс для мониторинга состояния агента, просмотра логов, метрик и управления локальным парсером через адресную строку.

Требования:
Создать модуль core/dashboard_state.py для сбора данных:
  Статус агента (на основе метрик и crash-репортов).
  Последний вызванный плагин и его статус (из interaction.log).
  Метрики из MetricsCollector.snapshot().
  Последние N строк из vasily.log (или фильтрованные по уровню).
  Список crash-репортов.
Сохранять собранные данные в dashboard_state.json (обновлять по запросу или через PeriodicScheduler раз в 5 секунд).

Создать интерфейс ui/dashboard.py на Streamlit:
  Верхняя панель: градиентный индикатор состояния (зелёный → красный) с текстовым пояснением («Работает», «Предупреждение», «Ошибка», «Упал»).
  Блок «Текущий плагин»: название последнего плагина, аргументы, статус; клик раскрывает детали (через st.expander). Ручной выбор режимов отсутствует (агент автономен).
  Блок «Логи»: сводный отчёт с возможностью копирования (кнопка «Копировать» через pyperclip или встроенные средства Streamlit). Добавить фильтры по уровню (ERROR, WARNING, INFO).
  Блок «Метрики»: карточки с числами (запросы, успехи, ошибки, среднее время, вызовы плагинов, заблокированные дубли).
  Блок «Локальный парсер»: поле ввода пути (адресная строка) с примером reports/sales.csv, кнопка «Прочитать файл», область вывода результата (таблица для CSV, форматированный JSON, текст), кнопка «Копировать содержимое».
  Блок «Файлы»: список файлов из папок data/ и reports/ с возможностью скачать или скопировать содержимое.

Копирование: все текстовые блоки должны позволять выделение (CSS: user-select: text), а также иметь кнопки копирования.

Обновление: дашборд автоматически обновляет данные (например, каждые 5 секунд через st.rerun или st.empty).

Запуск: отдельно от агента, через streamlit run ui/dashboard.py. Агент должен работать параллельно (данные читаются из файлов и логов).

Интеграция: Дашборд не вызывает плагины напрямую, а отправляет текстовые команды агенту (через тот же механизм, что и обычные сообщения) для выполнения операций (например, чтение файла через local_reader). Это сохраняет единую логику обработки запросов.

Примечание: Песочница (sandbox) для файлового доступа не реализуется как избыточная. Дашборд является надстройкой и не влияет на работу ядра.

QA-фокус: Проверить автообновление метрик, корректность отображения логов, работу кнопок копирования, интеграцию с локальным парсером через текстовые команды.

ПРЕДЛОЖЕНИЕ: Обратная интеграция Streamlit → Agent (ТЗ-ДОП-4)

Статус: Предложение на рассмотрение
Приоритет: Средний (после завершения ТЗ-ДОП-1, ТЗ-ДОП-2, ТЗ-ДОП-3)

Обоснование:
Текущая архитектура предполагает, что дашборд читает данные из файлов и логов, но не отправляет команды агенту. Для полноценного управления и тестирования необходима возможность отправлять запросы агенту прямо из интерфейса Streamlit.

Цель:
Создать механизм отправки текстовых команд агенту из дашборда и отображения результатов в реальном времени.

Варианты реализации:

Вариант А: HTTP API (рекомендуется)
  Добавить в core/agent.py простой HTTP-сервер (FastAPI или aiohttp) с эндпоинтом POST /api/request.
  Дашборд отправляет JSON: {"text": "прочитай reports/sales.csv"}.
  Агент обрабатывает запрос через handle_request() и возвращает результат.
  Преимущества: чистая архитектура, легко тестировать, можно использовать из других клиентов.

Вариант Б: Файловая очередь (упрощённый)
  Дашборд пишет запрос в data/incoming_requests.json.
  Агент читает файл через PeriodicScheduler (раз в 2-5 секунд).
  Результат пишется в data/outgoing_responses.json.
  Дашборд читает результат и отображает.
  Преимущества: не требует HTTP-сервера, проще в реализации.
  Недостатки: задержка, сложнее отладка, race conditions.

Вариант В: WebSocket (продвинутый)
  Агент запускает WebSocket-сервер.
  Дашборд подключается и отправляет/получает сообщения в реальном времени.
  Преимущества: мгновенная обратная связь, подходит для streaming-ответов.
  Недостатки: сложнее в реализации, требует управления соединениями.

Рекомендация: Начать с Варианта А (HTTP API) как наиболее универсального и тестируемого.

Требования (если утверждено):
  Создать core/api_server.py с эндпоинтом POST /api/request.
  Интегрировать с AgentCore.handle_request().
  Добавить в дашборд поле ввода команды и кнопку «Отправить».
  Отображать ответ агента в отдельном блоке с форматированием.
  Логировать все API-запросы в logs/api.log.

Тесты:
  Проверить отправку запроса через HTTP.
  Проверить корректность ответа.
  Проверить обработку ошибок (невалидный JSON, недоступный агент).

QA-фокус: Протестировать интеграцию дашборд ↔ агент, проверить что команды выполняются корректно, что результаты отображаются в интерфейсе.
