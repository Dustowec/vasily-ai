# ADR-001: Использование asyncio для асинхронности

## Статус
Принято

## Контекст
Агент "Василий" должен одновременно:
- Парсить сайты (30+ секунд)
- Генерировать арты через LLM (10-60 секунд)
- Отвечать пользователю в реальном времени
- Мониторить системные ресурсы

Проблема: При синхронном подходе (обычный Python) агент "замирает" во время долгих операций. Пользователь не может дать новую команду, пока агент ждёт ответ от сайта или LLM.

## Решение
Использовать асинхронное программирование через встроенный модуль syncio.

**Технический стек:**
- syncio — ядро асинхронности
- iohttp / httpx — асинхронные HTTP-запросы
- iofiles — асинхронная работа с файлами
- syncio.Queue — очереди задач

**Пример:**
\\\python
# Синхронно (плохо) — блокирует всё на 30 секунд
def sync_parse(url):
    response = requests.get(url)  # Ждём 30 сек, ничего не делаем
    return response.text

# Асинхронно (хорошо) — может делать другие задачи пока ждёт
async def async_parse(url):
    async with aiohttp.ClientSession() as session:
        async with session.get(url) as response:
            return await response.text()
\\\

## Последствия

### Положительные:
- ✅ Агент может обрабатывать несколько запросов одновременно
- ✅ Интерфейс не "замирает" во время долгих операций
- ✅ Эффективное использование ресурсов (один поток, много задач)
- ✅ Готовность к масштабированию (WebSocket, множественные пользователи)

### Отрицательные:
- ❌ Сложнее отлаживать (нужно понимать event loop)
- ❌ Нельзя использовать блокирующие библиотеки (например, equests)
- ❌ Все функции должны быть sync def — это "заразно"
- ❌ Сложнее для новичков

### Альтернативы, которые рассматривали:
1. **Мультипроцессинг** — отклонён, потому что требует больше памяти и сложнее в координации
2. **Мультитрединг** — отклонён, потому что Python имеет GIL (Global Interpreter Lock), который ограничивает параллелизм
3. **Celery + Redis** — отклонён, потому что избыточно для локального агента
