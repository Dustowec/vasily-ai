# ADR-003: Ollama over LM Studio

## Статус
Принято. Обновлено 2026-08-09 по результатам Фазы 1 и ревью аналитической группы.

## Контекст
Агенту Vasily AI требуется локальный LLM-сервер для работы в автономном режиме на потребительском железе. Модель должна поддерживать function calling для ReAct-паттерна, иметь достаточное контекстное окно и запускаться headless.

## Решение

### Выбор сервера: Ollama
Ollama предпочтён LM Studio по следующим причинам:
- Нативный REST API без зависимости от GUI.
- CLI-first дизайн, подходящий для headless-операций.
- Лучшая поддержка сообщества для function calling.
- Унифицированное поведение на всех платформах.
- Проще интегрировать автоподъём и health check.

### Выбор модели: Qwen2.5-3B abliterated
Базовая модель: `Qwen2.5-3B-instruct-abliterated-STF.Q4_K_S.gguf`
- Квантизация: Q4_K_S (баланс скорость/качество).
- Размер: 3B параметров.
- abliterated-сборка со снятыми ограничениями цензуры (осознанный выбор).
- Контекстное окно: 32k токенов (настраивается через `num_ctx` в Modelfile).

### Процедура регистрации модели
Кастомный GGUF регистрируется через Modelfile в корне проекта:

Modelfile содержит:
- `FROM` — путь к локальному GGUF-файлу.
- `PARAMETER temperature 0.1` — строгая температура для стабильного function calling.
- `PARAMETER num_ctx 32768` — явное указание контекстного окна.
- `PARAMETER top_p 0.9`.
- `TEMPLATE` — chat-шаблон модели.
- `SYSTEM` — системный промпт агента.

В коде `OllamaClient.DEFAULT_MODEL` указывает **имя регистрации** (`vasily-qwen`), а не исходный путь к GGUF.

### Архитектура клиента (реализовано в Фазе 1)

Класс `integrations/ollama_client.py` реализует:

1. **Асинхронность через aiohttp** (согласно ADR-001).
2. **Health check** через `/api/tags` с таймаутом 2 секунды.
3. **Retry с экспоненциальной задержкой**:
   - Строго 2 попытки (утверждено в ТЗ-015).
   - Backoff: 1 с → 2 с.
   - Полное время ожидания до провала: ~35 секунд.
4. **Graceful failure**: после исчерпания ретраев генерируется отчёт Crash Reporter и выбрасывается `LLMUnavailableError`.
5. **Передача `tools`** в `/api/chat` для function calling.
6. **Температура 0.1** зафиксирована как константа.
7. **Логирование каждого запроса** через structlog с прокидыванием `request_id` (ADR-004).

### Интеграция с Health Check (ТЗ-014)
`AgentCore.health_check()` при старте:
1. Выполняет до 3 попыток проверки доступности Ollama.
2. При неудаче агент переходит в **DEGRADED MODE**.
3. Печатает цветной отчёт с пометкой `LLM FAIL (DEGRADED MODE)`.
4. Агент продолжает работу с mock-плагинами, но без интеллектуальной маршрутизации.

### Обработка ошибок
Все исключения Ollama:
- Логируются на уровне ERROR (alert_level=CRITICAL_WARNING) с request_id.
- После исчерпания ретраев логируются на уровне CRITICAL (alert_level=CRASH).
- Генерируют crash-отчёт в `logs/crash_reports/`.
- Поднимаются выше для обработки в AgentCore.

## Последствия

### Положительные
- Агент работает полностью автономно без интернета.
- Восстановление после сетевых сбоев через retry.
- Наблюдаемость через структурированные логи каждого запроса.
- Деградация вместо полного отказа при недоступности LLM.

### Отрицательные
- Зависимость от доступности Ollama-сервиса на локальной машине.
- abliterated-сборка может давать менее предсказуемый output — требует отдельного тестирования (ТЗ-021).
- 32k контекст не гарантирован для всех сборок — требует проверки в ТЗ-018.

### Риски (для мониторинга)
- Длительная генерация при сложных запросах может превышать таймаут 30 с — решается увеличением `timeout` в Config при необходимости.
- OOM при исчерпании VRAM — отслеживается через будущие метрики (ТЗ-023).
