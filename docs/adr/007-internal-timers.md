# ADR-005: Внутренние таймеры и принцип нулевого доверия к внешним вызовам

- Статус: УТВЕРЖДЁН
- Дата: 2026-08-10
- Связано: ТЗ-022 (фоновый планировщик), отложенное предложение по Warm-памяти

## Контекст

Фаза 3 почти целиком состоит из периодических задач: фоновый планировщик,
мониторинг, автоподъём сервисов, резервное копирование, компрессия памяти.
Каждая требует таймера.

В отложенном предложении по Warm-памяти сброс warm→hot был сделан внутри
`ReActLoop.run()`, то есть срабатывал только при поступлении запроса
пользователя. Если агент простаивает — таймер не срабатывает никогда.
Это зависимость периодического тайминга от внешнего вызова.

Мы не доверяем, что внешние запросы будут приходить. Система должна сама
вести своё время. Это и есть «нулевое доверие» к внешним событиям.

## Решение

Все периодические и краткосрочные таймеры реализуются как внутренние фоновые
asyncio-задачи, стартующие вместе с агентом.

Правила:

1. Периодическая операция никогда не инициируется из обработчика запроса
   (`run()`, `handle_request()`). Обработчик может лишь оставить данные,
   но не запустить таймер.
2. Каждая периодическая задача при старте сверяется с персистентным
   состоянием (например, `last_updated` в файле), чтобы корректно пережить
   перезапуск агента.
3. При graceful shutdown все задачи останавливаются, а незавершённое
   состояние принудительно сбрасывается.
4. Событийные триггеры (например, «сбросить warm при shutdown») допустимы.
   Правило запрещает только периодический цикл, зависящий от внешнего вызова.

## Архитектура

Единый сервис-планировщик `PeriodicScheduler` (ядро ТЗ-022) владеет всеми
периодическими задачами:

    PeriodicScheduler
      ├── register(name, interval_seconds, coro_factory)
      ├── start()      # старт всех задач при запуске агента
      └── stop()       # graceful остановка + сброс состояния

Каждая задача — отдельный asyncio-цикл `while running: await task(); await
sleep(interval)`, изолированный try/except: падение одной задачи логируется,
но не убивает планировщик.

Существующий `_compression_worker` в MemoryManager становится одной из
зарегистрированных задач планировщика.

## Краевые случаи

1. Изоляция отказов: одна упавшая задача не роняет планировщик и не
   блокирует остальные.
2. Перезапуск: задачи читают персистентные метки времени, чтобы не
   «сбрасывать часы» при рестарте агента.
3. Graceful shutdown: планировщик останавливается последним, гарантируя
   финальный сброс.
4. Защита от дублей: задача не стартует повторно, если предыдущий прогон ещё
   выполняется (флаг «выполняется сейчас»).

## Последствия

Плюсы:
- Детерминированный тайминг, не зависящий от активности пользователя.
- Единообразие: все таймеры в одном месте, один жизненный цикл.
- Тестируемость: задачи можно запускать и проверять изолированно.

Издержки:
- Нужно управлять жизненным циклом задач (старт/стоп/отмена).
- Необходимо следить, чтобы event loop не блокировался, иначе таймеры
  asyncio будут запаздывать.
