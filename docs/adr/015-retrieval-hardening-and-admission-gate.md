# ADR-015: Retrieval hardening and admission gate — tokenization, LLM ranking, and secret filtering

Статус: Accepted
Дата: 2026-10-05
Суперсид: ADR-013 (разделы 4, 4.1, 5, 6, 9)
Автор: Архитектор (User)
Red team: TDD-цикл, 11 красных тестов до реализации (5 шагов)

## 1. Контекст

После ADR-013 память получила правильную термодинамику (зоны, score,
воскрешение), но retrieval остался на naive substring-поиске. Три
класса проблем были зафиксированы как красные флаги:

- «кот» in «который» → True — substring не различает границы слов;
- ранжирование только по score, без учёта релевантности запросу —
  случайное совпадение с высоким score обгоняло точное с низким;
- нагрев 5 фактов из manager, а LLM видит 3 (limit) — 2 из 5 обновляли
  last_heat_tick, искажая статистику остывания.

Дополнительно обнаружены две дыры:
- remember_fact мог записать пароль/токен в JSON-файл навсегда;
- внутренний дедуп в RememberFactTool вызывал recall_memory и сбрасывал
  _ticks_since_recall — активный режим остывания маскировался.

Документ фиксирует решения по всем пяти проблемам, порядок их внедрения
(TDD: красный тест → реализация → зелёный) и осознанные отказы
(BM25, FTS5).

## 2. Retrieval: токенизация и стемминг вместо substring

Функция `_find_candidates` сравнивает множества основ слов, полученных
Snowball-стеммером для русского.

Правила:
- вход и текст приводятся к lowercase **до** стемминга (Snowball сохраняет
  регистр: «Котофей» ≠ «котофей» без .lower());
- текст разбивается по `\w+` с re.UNICODE (кириллица входит);
- результат — set[str]: дедупликация + O(1) пересечение;
- match = непустое пересечение множеств.

Инвариант: «кот» ∩ «котор» = ∅ → мусор не находится.
Инвариант: stem(«коты») = stem(«кота») = «кот» → словоформы находятся.

Почему не pymorphy3: 20 МБ словарей против 200 КБ правил; для задачи
(диалоговая память ≤ 70 записей) точности Snowball достаточно.

Почему не BM25 / FTS5 (см. §6): ни одна из технологий не даёт русскую
морфологию из коробки, обе требуют того же стеммера. Корпус памяти
≤ 70 записей — O(N) мгновенен. Релевантность по смыслу отдана LLM (§3).

## 3. LLM-ранжирование кандидатов

Между retrieval и gate добавлен шаг: основная LLM получает список
кандидатов и возвращает JSON с номерами релевантных.

Механизм:
- retrieval отдаёт до 30 кандидатов (`MAX_RECALL_RESULTS: 5 → 30`);
- для каждого кандидата в промпт идёт превью ≤ 150 символов (не весь
  факт) — 30 × 150 ≈ 1500 токенов;
- LLM возвращает `{"ids": [1, 4, 7]}`;
- греются и показываются только выбранные.

Политика ошибок (параметр `on_error`):
- recall: `on_error="all"` — при сбое LLM возвращаются ВСЕ кандидаты
  (не теряем данные, лучше лишнее, чем потерять нужное);
- forget: `on_error="empty"` — при сбое возвращается ПУСТО
  (безопаснее: ничего не удалить из-за сетевого сбоя).

Единая точка правды: `memory/ranking.py` с общим механизмом
`_select_by_llm` и двумя обёртками:
- `rank_for_recall(llm, candidates, query)` — перед нагревом;
- `filter_for_forget(llm, topic, candidates)` — перед удалением.

AgentCore._llm_filter_forget стал тонкой обёрткой над `filter_for_forget`.

Обоснование против BM25: LLM понимает смысл («ноутбук ≈ комп»),
BM25 считает частоты. При наличии LLM в архитектуре BM25 — избыточный
слой. Вызов LLM на recall уже был (`_expand_query`), фактически мы
заменили один вызов на другой.

## 4. Инвариант «нагрев = показ»

`RecallMemoryTool._execute` меняет порядок операций:

Было:
  heated_keys = [f["key"] for f in result["facts"]]   # греем 5
  result["facts"] = result["facts"][:limit]            # показываем 3

Стало:
  result["facts"] = result["facts"][:limit]            # сначала обрезаем
  heated_keys = [f["key"] for f in result["facts"]]   # греем ровно показанные

Причина: 2 из 5 фактов обновляли last_heat_tick, не попадая в контекст
LLM. Это искажало динамику остывания и «утекало» score вверх.

Инвариант закреплён тестом `test_heat_equals_display_3_of_10` и
`test_no_heat_when_nothing_found`.

## 5. Разделение recall_memory на три ступени

Одна функция смешивала три измерения. Разделена на три изолированные
ступени с явными контрактами:

- `_find_candidates(query_tokens)` — retrieval. Знает только про
  токенизацию. Не сортирует. Не обрезает.
- `_rank_by_zone_score(candidates)` — rerank. Знает только про
  zone_score. Не знает про запрос.
- `_gate_for_output(ranked, limit)` — gate. Знает только про лимит.

`recall_memory` стал тонким оркестратором. Точки расширения: BM25 (если
когда-нибудь) тронет только `_find_candidates`; фильтр мусора (если
когда-нибудь) — только `_gate_for_output`.

## 6. Admission gate: секреты не попадают в память

Единственный гейт в `GradientMemory._store_entry` — самая нижняя точка
записи. Никто не обойдёт: ни RememberFactTool, ни фоновая компрессия
диалога, ни будущие пути.

Фильтруем:
- пары «секретный_ключ: значение» — password|passwd|pwd|passphrase|
  secret|token|api_key|access_key|auth_token|пароль|токен;
- «Bearer <token>», если токен содержит цифры ИЛИ длина ≥ 20;
- префиксные токены провайдеров: sk-, ghp_, gho_, xoxb-, AIza;
- длинные base64-подобные строки (40+ символов) со смешанным регистром
  и цифрами.

Не фильтруем:
- «эфемерное» (погода, время) — слишком много ложных срабатываний;
  «люблю когда холодно» — это предпочтение, не мусор;
- монотонные заглушки («xxxxx…», «aaaaa…») — не секреты, а тестовые
  значения;
- «Bearer authentication» — слово, а не токен.

Контракт `_store_entry` изменён: возвращает dict
`{"stored": bool, "reason"?: str, "key"?: str}` вместо None.

Следствия:
- `remember_user_fact` / `remember_dialogue_summary` / `remember`
  возвращают этот dict;
- `RememberFactTool` проверяет `stored` и возвращает
  `{"status": "rejected", "reason": ...}` — LLM скажет пользователю
  почему не записала;
- `AgentCore._compress_and_store_dialogue` логирует отклонение
  (фоновая задача — некому «сказать», но потеря памяти не должна
  оставаться незамеченной).

Счётчик `_ticks_since_write` при admission-reject НЕ сбрасывается:
отклонённая запись — это попытка, а не запись.

## 7. Разделение счётчиков recall / write

Проблема: RememberFactTool внутри вызывает recall_memory для дедупа.
Это сбрасывало `_ticks_since_recall`, и активный режим остывания не
включался, хотя пользователь память НЕ читал.

Решение:
- `recall_memory(query, external=True)`:
    True  — публичный вызов (LLM/пользователь читает память),
            сбрасывает `_ticks_since_recall`;
    False — внутренний дедуп, счётчик НЕ трогает.
- `RememberFactTool._execute` передаёт `external=False`.
- Новый счётчик `_ticks_since_write`:
    инкрементируется в decay() вместе с recall-счётчиком;
    сбрасывается в _store_entry после успешного admission + lock;
    НЕ сбрасывается при admission-reject.
- `get_stats` отдаёт оба счётчика. active_mode по-прежнему
  определяется только через recall-счётчик.

## 8. Порядок внедрения (TDD)

Каждый шаг — красный тест → реализация → зелёный:

- Шаг 0 (fix): нагрев ровно показанных.
  Тест: `test_heat_equals_display.py::test_heat_equals_display_3_of_10`.
  Красный показал «нагрето 5, ожидалось 3».
- Шаг 1 (refactor): разделение recall_memory на три ступени.
  Без нового теста — рефакторинг под защитой существующих 321 теста.
- Задача №3 (feat): LLM-ранжирование.
  Тесты: `test_llm_ranking.py` (2 кейса).
  Красный показал: «кот» и «который» оба попадают в ответ и оба греются.
- Шаг 2 (refactor): токенизация + стемминг.
  Тесты: `test_tokenizer.py` (6 кейсов).
  Красный: ModuleNotFoundError (модуля нет — указывает на цель).
- Шаг 3 (feat): admission gate.
  Тесты: `test_admission.py` (40 кейсов).
  Три итерации красных — каждая указывала на реальный баг regex:
  (1) «Bearer xyz» не ловился — узкий паттерн;
  (2) «xxxxx…» ловился — широкий паттерн на long_random;
  (3) «Bearer authentication» ловился — снова широкий Bearer.
- Шаг 4 (refactor): разделение счётчиков.
  Тесты: `test_recall_write_counters.py` (7 кейсов).
  Красный: 5 падений — AttributeError, TypeError, KeyError,
  assert 0 == 7.

Итог: 376 passed (было 319 до итерации).

## 9. Осознанные отказы

BM25 — отменён (§3).
FTS5 / SQLite — отменён (§2).
Векторные эмбеддинги — вне обсуждения (противоречит ADR-013 §9:
«трассируемые числа», прозрачность, отсутствие локального инференса).

## 10. Открытые вопросы

- `pyproject.toml` в репозитории отсутствует, `uv.lock` осиротел.
  `snowballstemmer` зафиксирован в `requirements.txt` как временное
  решение. Отдельная задача: восстановить `pyproject.toml`, мигрировать
  управление зависимостями под uv.
- «Эфемерное» в admission gate (погода, время, курсы) сознательно не
  фильтруется из-за высокого уровня ложных срабатываний. Требует
  отдельного анализа, если появится реальная проблема.
