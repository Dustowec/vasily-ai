# ADR-017: task_state — канал активных задач

- **Дата:** 2026-10-07
- **Статус:** Принято
- **Контекст:** HANDOFF §7.2 (открытый вопрос про автономные задачи)
- **Связано:** ADR-013 (Gradient Cascade Memory), ADR-015 (retrieval hardening)

---

## 1. Контекст и проблема

### 1.1. Что есть сейчас

Память агента (ADR-013) хранит два канала:

- **`user_fact:*`** — факты о пользователе. Создаются явной командой
  («запомни»), score 40, амнистия 10 тиков при `forget_all`.
- **`dialogue_summary:*`** — конспекты диалога. Создаются автоматически
  при компрессии, score 15, обычная термодинамика.

Оба канала **пассивны**: они описывают «что было», а не «что делать».
Это правильно для фактов и конспектов, но недостаточно для задач.

### 1.2. Проблема

Если пользователь ставит агенту долгую задачу — «напиши парсер логов,
горизонт — несколько сессий, с чек-поинтами» — она **не сохраняется
как единица работы**:

- `dialogue_summary` даст размытое «говорили о парсере логов», без
  структуры (что за цель, что сделано, что дальше);
- `user_fact` не подходит — факт статичен, задача движется;
- в оперативной памяти (ReAct-цикл) задача живёт только до конца
  текущей сессии и умирает вместе с контекстом.

При рестарте агента незавершённая работа теряется.

### 1.3. Что решаем

Ввести третий канал памяти — `task_state:*` — для **активных задач**,
которые:

- имеют цель (goal),
- имеют статус (`in_progress` / `done` / `cancelled`),
- накапливают прогресс (шаги + чек-поинты),
- переживают рестарт агента,
- **не остывают и не дистиллируются**, пока активны,
- управляются инструментом `long_task`,
- автоматически попадают в system prompt LLM (вариант B из обсуждения).

## 2. Термины

**Задача** — намерение выполнить действие, которое:
- требует больше одного шага ИЛИ имеет горизонт дольше одной сессии,
- имеет измеримую цель,
- может накапливать прогресс,
- имеет жизненный цикл.

**Задача — это НЕ:**
- факт («меня зовут Вася») — факт статичен;
- конспект (`dialogue_summary`) — конспект описывает прошлое;
- напоминание на одну сессию — такое не нужно сохранять в память.

## 3. Рассмотренные альтернативы

### 3.1. Где хранить задачи

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Только `user_fact`** | Не трогаем память | Смешение семантики: факт ≠ процесс. Нет полей `status`, `steps`, `checkpoints`. Термодинамика не различает «активно»/«сделано». | ❌ Отклонено |
| **B. Новый канал `task_state:`** | Единая память, единая термодинамика, категоризация по префиксу уже есть. Минимум переделок. | Записи с особым поведением в `decay`. | ✅ **Принято** |
| **C. Отдельная зона `_tasks`** | Полная изоляция от термодинамики. | Большая переделка: четыре зоны вместо трёх, `_load_all`, `_save_all`, `forget_all`, `recall_memory`, `compress_cycle` — всё надо трогать. Изоляция нужна там, где логика принципиально иная, а здесь — те же свойства плюс защита. | ❌ Отклонено |

**Обоснование:** канал `task_state` — это тот же тип записи, что
`user_fact`, но с дополнительной защитой от остывания. Отдельная
зона — избыточна. Принцип «не переусложняй» (HANDOFF §11).

### 3.2. Как защищать активные задачи от остывания

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Freeze в `decay`** | Просто, локально, тестируется за минуты. Не трогает существующую логику зон. | Особый случай в общем цикле. | ✅ **Принято** |
| **B. Отдельная зона** | См. 3.1C. | Избыточно. | ❌ Отклонено |
| **C. Медленное остывание (например, `−0.01`/тик)** | Мягко, не ломает термодинамику. | Задача всё равно дойдёт до порога дистилляции — просто позже. Не решает проблему, только откладывает. | ❌ Отклонено |

**Обоснование:** задача `in_progress` не должна остывать **вообще**.
Это семантическое требование: незавершённая работа не «теряет
ценность» от времени. Freeze — прямое выражение этого требования.

### 3.3. API инструмента `long_task`

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Один `long_task` с `action`** | Минимум дублирования схемы. Все действия — в одном описании для LLM. Пользователь видит один инструмент, а не четыре. | Меньше изоляции между операциями. | ✅ **Принято** |
| **B. Четыре отдельных инструмента** (`task_create`, `task_progress`, `task_complete`, `task_list`) | Разделение ответственности. | Раздувает список инструментов, дублирует общую валидацию, LLM путается в схемах. | ❌ Отклонено |
| **C. CLI-подобный (`long_task(command="create ...")`)** | Гибко. | Парсинг строки — источник ошибок, LLM плохо генерирует структурированные команды. | ❌ Отклонено |

**Обоснование:** операций мало, они логически родственны. Один
инструмент с явным enum-параметром `action` — идиоматично и
компактно.

### 3.4. Доставка активных задач в контекст LLM

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Только явный recall** | Просто, ничего не трогаем в ReAct. | LLM может «забыть» проверить память — исходная проблема не решается. | ❌ Отклонено |
| **B. Автоинъекция в system prompt** | Задачи всегда перед глазами LLM, независимо от запроса. | Трогаем `golden_prompts.py` / `react_loop.py`. Расход токенов на каждой итерации. | ✅ **Принято** |
| **C. Подсказка в промпте** («если задача долгая — вызови `long_task list`») | Компромисс. | Зависит от того, вспомнит ли LLM. Не гарантирует. | ❌ Отклонено |

**Обоснование (твоё):** «иначе это просто баловство». Если задача не
перед глазами LLM — она с большой вероятностью будет проигнорирована
до явного запроса пользователя. Автоинъекция — единственный вариант,
который решает проблему «агент забыл про незавершённую работу».

### 3.5. Статусы

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. Минимум: `in_progress` / `done` / `cancelled`** | Покрывает все реальные сценарии. | Нет «паузы» и «блокировки». | ✅ **Принято** |
| **B. Расширенный: + `blocked` / `paused`** | Гибче. | Семантически пересекается с `in_progress`: «пауза» — это тоже выполняется, просто не сейчас. Оверкилл до появления реальных сценариев. | ❌ Отложено (в будущий ADR) |

**Обоснование:** минимум, который покрывает всё, что есть сейчас.
Промежуточные статусы — на карандаш, если появится реальный кейс.

## 4. Решение

### 4.1. Семантика задачи

Задача — **активная единица работы** с целью, статусом и накоплением
прогресса. Не факт, не конспект. Отличается от `user_fact` наличием
полей `status`, `steps`, `checkpoints` и особым поведением в
термодинамике.

### 4.2. Структура данных

**Ключ:** `task_state:<hex>` — генерируется автоматически через
`uuid4().hex[:8]`. Никаких пользовательских slug'ов (см. §5.2).

**Значение (`value`):**

```json
{
  "goal": "написать парсер логов",
  "status": "in_progress",
  "steps": [
    {"text": "разобрать формат", "done": true},
    {"text": "написать читалку", "done": false}
  ],
  "checkpoints": [
    {"tick": 5,  "note": "формат разобран: JSON lines"},
    {"tick": 12, "note": "читалка готова наполовину"}
  ],
  "created_tick": 0,
  "updated_tick": 12
}
```

- `goal` — человекочитаемое описание цели.
- `status` — `in_progress` | `done` | `cancelled`.
- `steps` — заранее намеченный план (чек-лист «что делать»).
- `checkpoints` — журнал «что уже сделано».
- `created_tick` / `updated_tick` — тики создания и последнего
  изменения.

`steps` и `checkpoints` **оба присутствуют** (решение из обсуждения):
они отвечают на разные вопросы и не заменяют друг друга.

### 4.3. Жизненный цикл и статусы

| Статус | Смысл | Термодинамика |
|---|---|---|
| `in_progress` | Выполняется | `score` **заморожен на 40**, `no_compress=True`, зона не меняется |
| `done` | Завершена успешно | `no_compress` снимается, `score` **остаётся 40**, начинается обычное остывание |
| `cancelled` | Отменена пользователем | То же, что `done` |

**Про `score` после `done` (решение из обсуждения — вариант «a»):**
`score` остаётся 40, не падает до 15. Обоснование: воспоминания о
задаче могут понадобиться через несколько шагов после её завершения
(особенно если задача была крупной и декомпозированной пользователем).
Дольше живёт — ниже риск потерять контекст.

При `DECAY_HOT_BASE = −0.3`/тик путь с 40 до порога дистилляции
(`DISTILL_TRIGGER = 5.0`) занимает ~117 тиков. Это намного больше
любого реалистичного горизонта возврата к завершённой задаче.

### 4.4. Защита от остывания (freeze)

В `decay()`, для каждой зоны (`_tgs`, `_hot`, `_cold`):

```
для каждой entry:
    если key.startswith("task_state:") и value.status == "in_progress":
        пропустить (score не менять, из зоны не выселять,
                    в _distill_queue не класть)
```

Freeze — **основная защита**. Достаточна сама по себе: если freeze
работает, задача не может ни дистиллироваться, ни мигрировать в COLD,
ни потерять score.

### 4.5. Взаимодействие с `forget_all` и дистилляцией

**При `forget_all`:**
- Активные `task_state:*` (`in_progress`) **амнистируются** так же, как
  свежие `user_fact` (10 тиков). «Забудь всё» не убивает незаконченную
  работу.
- `done` и `cancelled` задачи — обычные записи, участвуют в ротации.

**При дистилляции (`compress_cycle`):**
- Активные `task_state:*` помечаются флагом `no_compress=True` при
  создании.
- `no_compress=True` не даёт задаче попасть в дистилляцию (при
  `score <= DISTILL_TRIGGER=5.0`).
- **Вторая линия защиты:** даже если freeze по какой-то причине
  откажет и `score` начнёт падать — пока он не достиг
  `MIGRATION_TRAP=0.5`, задача останется в HOT. С 40 это ~130 тиков
  (−0.3/тик), что даёт достаточно времени обнаружить баг.
- При переходе в `done` / `cancelled` — `no_compress` снимается,
  задача идёт обычным путём.

**Про формулировку из обсуждения.** «С `no_compress` ловушка не
сработает» — верно по итогу, но по причине, а не по механизму:
`no_compress=True` **включает** `MIGRATION_TRAP`, а не отключает
её. От дистилляции защищает именно `no_compress`. От миграции —
**freeze**: он не даёт `score` дойти до 0.5. Два независимых
механизма, каждый страхует свой участок.

### 4.6. Инструмент `long_task`

Один инструмент, параметр `action` (enum). Все действия — в одном
описании схемы.

| `action` | Параметры | Что делает |
|---|---|---|
| `create` | `goal`, `steps?` (список строк) | Создаёт `task_state:<hex>` со статусом `in_progress`, `score = 40`, `no_compress = True`. `steps` превращаются в список `{text, done: false}`. |
| `checkpoint` | `key`, `note` | Добавляет запись в `checkpoints` с текущим `total_ticks`. Обновляет `updated_tick`. |
| `step_done` | `key`, `step_index` | Помечает `steps[step_index].done = true`. Обновляет `updated_tick`. |
| `complete` | `key` | `status = "done"`, снимает `no_compress`. `score` остаётся 40. |
| `cancel` | `key` | `status = "cancelled"`, снимает `no_compress`. |
| `list` | — | Возвращает два списка: `in_progress` и `done`. Каждый элемент — `{key, goal, updated_tick}`. `cancelled` в список не попадает (доступен через `get`). |
| `get` | `key` | Полная карточка задачи (все поля `value`). |
| `help` | — | Возвращает список действий с кратким описанием **на русском языке** для LLM. |

Возвращаемое значение всех действий — словарь с полем `status`
(`success` / `error` / `not_found`) и полезной нагрузкой.

### 4.7. Автоинъекция активных задач в system prompt

**Где:** при формировании system prompt для LLM в `react_loop` /
`AgentCore` — до первого сообщения пользователя в итерации.

**Что:** метод у `GradientMemory`: `get_active_tasks() -> list[dict]`,
возвращает `{key, goal, last_checkpoint}` для активных (`in_progress`)
задач, отсортированных по `updated_tick` (свежие сверху).

**Формат инъекции** (черновой, уточним при реализации):

```
[АКТИВНЫЕ ЗАДАЧИ]
У тебя есть незавершённые задачи. Учти их перед ответом:
- task_state:a1b2c3d4: написать парсер логов
  последний чек-поинт (t=12): читалка готова наполовину
- task_state:e5f6g7h8: изучить документацию API
```

**Ограничение:** максимум **3** задачи в инъекции (по `updated_tick`).
Если активных больше — остальные доступны через `long_task list`.

**Если активных задач нет** — блок не добавляется.

### 4.8. Категоризация и дедуп

Префикс `task_state` уже включён в:

- `KNOWN_CATEGORIES` — `memory/manager.py`;
- `DEDUP_CATEGORIES` — `memory/manager.py`.

Это означает:
- `recall_memory(..., categories=["task_state"])` работает из коробки;
- дедуп в `RememberFactTool` автоматически проверяет `task_state` —
  при попытке создать `user_fact`, дублирующий задачу, дедуп сработает.

Никаких изменений в `memory/manager.py` для категоризации не требуется
(заложено в фиксе дедупа `b634726`).

## 5. Обоснование ключевых решений

### 5.1. Почему префикс ключа, а не поле в entry

Единый стиль категоризации во всём проекте (см. §6 HANDOFF). Поле
`category` требовало бы миграции существующих записей и второго
источника правды. Префикс — уже сложившийся контракт.

### 5.2. Почему `uuid`, а не slug

- Slug (`task_state:log-parser`) — соблазн для коллизий: два разных
  пользователя / две разные сессии / перефразирование одной задачи
  дадут разные slug'и или, что хуже, одинаковый slug для разных задач.
- Автоматический hex гарантирует уникальность.
- Человекочитаемое имя — в поле `goal`, не в ключе.

### 5.3. Почему `steps` и `checkpoints` оба

- `steps` — **план**. Задаётся при создании, отвечает на вопрос «что
  предстоит сделать».
- `checkpoints` — **журнал**. Растёт по ходу работы, отвечает на
  вопрос «что уже сделано и как».

Можно было бы вести только журнал и восстанавливать план из него,
но это требует LLM-парсинга при каждом запросе. Явные `steps` —
дешевле и надёжнее.

### 5.4. Почему freeze, а не медленное остывание

Незавершённая работа не должна «дешеветь» от времени. Медленное
остывание лишь откладывает потерю. Freeze — прямое выражение
семантики.

### 5.5. Почему автоинъекция в промпт, а не recall

Если задача не перед глазами LLM, она будет проигнорирована до
явного напоминания пользователя. Ровно та проблема, которую решает
этот ADR. Без автоинъекции — фикс неполный.

### 5.6. Почему один инструмент с `action`

Операций мало, они логически родственны. Один инструмент = одна
схема, одно описание для LLM, один код валидации общих параметров
(`key`). Четыре отдельных инструмента раздувают и без того
немаленький список доступных действий.

## 6. Последствия

### 6.1. Что меняется в коде

**`memory/manager.py`:**
- Метод `remember_task_state(key, value) -> dict` (по аналогии с
  `remember_user_fact`, `remember_dialogue_summary`).
- Метод `update_task_state(key, patch) -> dict` — точечное обновление
  (status, steps, checkpoints).
- Метод `get_active_tasks() -> list[dict]` — для автоинъекции в
  промпт.
- В `decay()` — freeze для активных `task_state`.
- В `forget_all()` — амнистия активных `task_state` (как для свежих
  `user_fact`).

**`core/internal_tools.py`:**
- Новый класс `LongTaskTool(BaseTool)` со всеми `action`.

**`core/golden_prompts.py`** (или где формируется system prompt):
- Сборка блока `[АКТИВНЫЕ ЗАДАЧИ]` из `get_active_tasks()`.
- Вставка блока в system prompt перед первым сообщением пользователя.

**`core/plugin_registry.py`** (или где регистрируются инструменты):
- Регистрация `LongTaskTool`.

### 6.2. Что НЕ делаем в этом ADR

- ❌ Автоизвлечение задач из диалога при компрессии — **ADR-018**.
- ❌ Автоматическая декомпозиция цели на шаги через LLM — **ADR-019**.
- ❌ Промежуточные статусы `blocked` / `paused` — на карандаш.
- ❌ Синхронизация с внешними TODO — не планируется.
- ❌ Иерархия задач (task → subtask) — плоско.
- ❌ Отдельная зона памяти под задачи — см. §3.1.

### 6.3. Открытые вопросы на будущее

- **Автоизвлечение задач** при компрессии `dialogue_summary` (ADR-018):
  если LLM заметила в диалоге «задачу», но `long_task create` не был
  вызван — стоит ли создавать `task_state` автоматически?
- **Промежуточные статусы** (`blocked`, `paused`) — по появлении
  реального сценария.
- **Автодекомпозиция** цели на шаги через LLM — по появлении
  сценария с действительно сложными задачами.

## 7. Тесты (TDD)

Порядок: сначала красные тесты, потом код.

**`tests/test_task_state_creation.py`:**
- создание задачи: ключ начинается с `task_state:`, `score = 40`,
  `no_compress = True`, `status = "in_progress"`;
- поля `goal`, `steps`, `checkpoints`, `created_tick`, `updated_tick`
  на месте.

**`tests/test_task_state_decay_freeze.py`:**
- после N тиков `decay()` активная задача не меняет `score`, не
  покидает зону, не попадает в `_distill_queue`;
- после `complete` задача начинает остывать обычным темпом;
- после `cancel` — то же.

**`tests/test_task_state_forget_all_amnesty.py`:**

- `done` и `cancelled` — не амнистируются.

**`tests/test_long_task_tool.py`:**
- все действия: `create`, `checkpoint`, `step_done`, `complete`,
  `cancel`, `list`, `get`, `help`;

- `list` возвращает два списка (`in_progress`, `done`);

**`tests/test_task_state_prompt_injection.py`:**

  по `updated_tick`;
- ограничение топ-3;
- пустой список, если активных нет.

**`tests/test_recall_task_state.py`:**
- `recall_memory(..., categories=["task_state"])` работает;
- `dialogue_summary` и `user_fact` отсекаются.
