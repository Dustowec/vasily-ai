##ADR-012: Градиентно-каскадная память с семантической дедупликацией и адаптивным охлаждением
Дата: 2026-08-30
Статус: Accepted
Суперседает: ADR-009 (Gradient Cascade Memory Architecture)
Автор: Архитектор (User) + Tech Lead (Implementation)
Контекст: Переработка архитектуры памяти после выявления проблем с дублированием фактов, неэффективным охлаждением и отсутствием семантического поиска.

1. Контекст и проблема
После внедрения ADR-009 выявлены следующие критические проблемы:
Дублирование фактов: Пользовательские факты дублируются при повторных запросах с разной формулировкой (например, "у меня есть кот Барсик" и "моего кота зовут Барсик").
Дублирование системных саммари: Диалоговые саммари, создаваемые LLM-компрессором, дублируют уже сохранённые пользовательские факты.
Неэффективное охлаждение: Текущая формула decay_actual = max(0.01, 0.1 - (count_requests * 0.0003)) приводит к "болоту" — мусор в HOT-зоне остывает слишком медленно при длинных сессиях.
Отсутствие семантического поиска: recall_memory ищет только по точному совпадению слов, не находя факты при несовпадении формулировок.
Перекос приоритетов: Длинные диалоговые саммари получают высокий приоритет, а короткие пользовательские факты — низкий.

2. Предлагаемое решение
Внедрить трёхкомпонентную архитектуру:
Трёхуровневое охлаждение с адаптивным режимом — разные скорости распада для разных зон и уровней активности.
Семантическая дедупликация — LLM-based сравнение фактов с кэшированием результатов.
Профилактика дублирования саммари — передача контекста известных фактов в LLM-компрессор.

3. Детальная спецификация

3.1. Зоны памяти и диапазоны
Зона Диапазон score  Базовый распад  Активный распад         Вход                                            Выход
TGS  50.0..60.0	     -0.1/тик        -0.1/тик (не меняется)  score ≥ 50.0                                    score < 50.0 → миграция в HOT (score=40)
HOT  +5.1..49.9      -0.3/тик        -0.7/тик                score=15 (системное) или 40 (пользовательское)  score < -50.0 → удаление; score ≥ 50.0 → TGS
COLD -50.0..-5.0     -0.5/тик        -1.5/тик                score=-5.0 (фиксированный при миграции из HOT)  score < -50.0 → удаление

Критические параметры:
Потолок нагрева HOT/COLD: 49.9 (не 100.0, как ранее)
TGS лимит: 10 фактов с вытеснением по наименьшему скору
Миграция HOT→COLD: диапазон 5.0..-4.0 с назначением штрафа -10 к score
Recall из COLD: +10, возврат в HOT с protected=True

3.2. Активный режим
Условие активации: Отсутствие вызовов recall_memory за последние 10 запросов.
При переходе в активный режим:
HOT: распад ускоряется с -0.3 до -0.7/тик
COLD: распад ускоряется с -0.5 до -1.5/тик
TGS: распад остаётся -0.1/тик (не меняется)
Логика: Если пользователь не обращается к памяти, система ускоряет очистку мусора, но защищает конституцию (TGS).

3.3. Нагрев (Heating)
Действие                    Прирост score         Примечание
recall_memory               +5.0                  Не выше 49.9 для HOT/COLD
remember_fact (новый факт)  +10.0                 Создаёт с score=40 (пользовательский)
remember_fact (дубликат)    +15.0                 Нагрев существующего факта
remember_fact (дополнение)  +10.0                 Обновление значения через LLM
Recall из COLD              +10.0                 Возврат в HOT с protected=True

3.4. Семантическая дедупликация (LLM-based)
Алгоритм:
При вызове remember_fact → LLM извлекает ключевые слова из нового факта.
Вызов recall_memory с этими ключевыми словами.
Если найден похожий факт → LLM сравнивает множества ключевых слов:
Пересечение ≥ 80% → ДУБЛЬ → нагрев +15
Пересечение < 80% → ДОПОЛНЕНИЕ → нагрев +10 + обновление значения через LLM
Примеры:
"у меня есть кот барсик" / "моего кота зовут барсик" → ДУБЛЬ (ключевые слова: кот + барсик)
"у меня есть кот барсик" / "мой кот барсик любит рыбу" → ДОПОЛНЕНИЕ (ключевые слова: кот + барсик + рыба)
Кэширование: Результаты LLM-сравнения кэшируются в рамках сессии. Если один и тот же факт повторяется — повторный LLM-вызов не делается.
Fallback: Если LLM недоступен — используется эвристика по длине (ratio > 0.6 → дубликат).
Стоимость: +0.5 сек задержки на каждый remember_fact, 0 МБ дополнительной VRAM.

3.5. Защита от дублирования системных саммари
Проблема: LLM-компрессор создаёт саммари диалога, которое может дублировать уже сохранённые пользовательские факты.
Решение:
1. Перед компрессией диалога → получить топ-3 факта из HOT-памяти через recall_memory.
2. Передать эти факты в промпт LLM-компрессора с инструкцией: "Не включай в резюме то, что уже есть в этом списке".
3. LLM-компрессор возвращает саммари без дублирования.
Пример промпта:
Сделай краткое резюме следующего текста в 2-3 предложениях.
УЖЕ ИЗВЕСТНЫЕ ФАКТЫ (НЕ ПОВТОРЯЙ ИХ В РЕЗЮМЕ):
- "Моего кота зовут Барсик" | "Пользователь работает над проектом X"

Текст для сжатия:
[диалог]
Стоимость: 0 МБ VRAM, +0.5 сек задержки на компрессию.

4. Схема переходов

Создание (score=15 для системного, 40 для пользовательского)
    ↓
HOT (score 5.1..49.9)
    ↓ (компрессия при score 5.0..-4.0, штраф -10)
COLD (score=-5.0 фиксированный)
    ↓ (recall +10, protected=True)
HOT (score +10) ← возврат в HOT с защитой
    ↑ (score ≥ 50.0)
TGS (score 50.0..60.0) ← защищённая зона, лимит 10
    ↓ (score < 50.0)
HOT (score=40) ← миграция в HOT со скором 40
    ↓ (score < -50.0)

5. Математика охлаждения

5.1. Базовый режим (есть recall за последние 10 запросов)

Зона                    Распад        Время жизни до удаления
HOT (score=40)          -0.3/тик      150 тиков
HOT (score=15)          -0.3/тик      65 тиков
COLD (score=-5.0)       -0.5/тик      90 тиков
TGS (score=55.0)        -0.1/тик      ~50 тиков до миграции в HOT

5.2. Активный режим (нет recall за 10 запросов)

Зона                     Распад       Время жизни до удаления
HOT (score=40)           -0.7/тик     57 тиков
HOT (score=15)           -0.7/тик     21 тик
COLD (score=-5.0)        -1.5/тик     30 тиков
TGS (score=55.0)         -0.1/тик     ~50 тиков (не меняется)

6. Примеры сценариев
Сценарий 1: Дубликат пользовательского факта
Запрос 1: "Запомни: моего кота зовут Барсик"
LLM извлекает ключевые слова: [кот, барсик]
recall_memory → не найдено
Создаётся новый факт с score=40
Запрос 2: "Запомни: у меня есть кот по имени Барсик"
LLM извлекает ключевые слова: [кот, барсик]
recall_memory → найден факт "моего кота зовут Барсик"
LLM сравнивает множества: пересечение 100% → ДУБЛЬ
Нагрев существующего факта: +15 → score=55.0
Ответ: "Я уже знаю этот факт и обновил его приоритет в памяти."
Сценарий 2: Дополнение пользовательского факта
Запрос 1: "Запомни: моего кота зовут Барсик"
Создаётся факт с score=40
Запрос 2: "Запомни: мой кот Барсик любит рыбу"
LLM извлекает ключевые слова: [кот, барсик, рыба]
recall_memory → найден факт "моего кота зовут Барсик"
LLM сравнивает множества: пересечение 67% (< 80%) → ДОПОЛНЕНИЕ
Нагрев +10 → score=50.0
Обновление значения через LLM: "Моего кота зовут Барсик. Он любит рыбу."
Ответ: "Факт обновлён с новой информацией."
Сценарий 3: Защита от дублирования саммари
Диалог:
Пользователь: "Запомни: моего кота зовут Барсик"
Ассистент: "Факт сохранён."
Пользователь: "А что ты запомнил?"
Ассистент: "Твоего кота зовут Барсик."
Компрессия диалога:
Получаем топ-3 факта из HOT: ["Моего кота зовут Барсик"]
Передаём в LLM-компрессор с инструкцией не повторять
LLM возвращает: "Пользователь спросил о сохранённых фактах, ассистент подтвердил наличие информации о коте Барсике."
Саммари НЕ дублирует факт "Моего кота зовут Барсик"

11. Миграция данных

11.1. Автоматическая миграция
При первом запуске после внедрения ADR-012:
TGS: Файл tgs_memory.json остаётся без изменений.
HOT: Файл tg_hot_memory.json:
Факты с score > 49.9 → мигрируют в TGS (если есть место)
Факты с score < 5.1 → мигрируют в COLD с score=-5.0
COLD: Файл tg_cold_memory.json остаётся без изменений.

11.2. Ручная миграция (опционально)
Если нужна полная очистка:
Remove-Item data\tgs_memory.json
Remove-Item data\tg_hot_memory.json
Remove-Item data\tg_cold_memory.json

12. Обратная совместимость

12.1. API
Метод remember() остаётся для обратной совместимости, но internally вызывает remember_user_fact() или remember_dialogue_summary() в зависимости от контекста.
Новые методы remember_user_fact(), remember_dialogue_summary(), heat_fact() — публичные.

12.2. Формат данных
Формат JSON-файлов памяти не меняется.
Добавляются новые поля: recalled (для отслеживания вызовов recall в активном режиме).
13. Заключение
ADR-012 решает все критические проблемы, выявленные после внедрения ADR-009:
Дублирование фактов → LLM-based дедупликация с кэшированием
Дублирование саммари → Передача контекста известных фактов в LLM-компрессор
Неэффективное охлаждение → Трёхуровневое охлаждение с адаптивным режимом
Отсутствие семантического поиска → LLM Query Expansion (уже реализовано)
Перекос приоритетов → Явные методы записи с жёсткими приоритетами
Архитектура остаётся в рамках 0 МБ дополнительной VRAM, добавляя +0.5 сек задержки на операции дедупликации, что приемлемо для агента.
