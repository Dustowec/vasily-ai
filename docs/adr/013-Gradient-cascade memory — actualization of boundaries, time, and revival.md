1. Контекст
После ревью кода и двух раундов красной команды устранён дрейф «спека ≠ замысел ≠ код»: семантика TGS, потолок нагрева, механика воскрешения, лестница промоции, enforcing лимитов нагрева. Документ фиксирует фактическую архитектуру памяти с трассируемыми числами.

Ключевое переосмысление: TGS — не «конституция», а рабочий кэш топ-10 фактов, которые юзер реально использует. Смертный, как вся память.

2. Семантика зон
Зона
Роль
Score-пул
TGS (Thermal Group Shield)	Рабочая зона: топ-10 фактов, которые юзер реально использует. Кэш, не истина	50.0–60.0
HOT	Точка входа и фильтр: важное живёт и растёт, неважное отлетает	0.1–49.9

Принцип: бессмертной памяти нет. Любой факт умирает от неиспользования; каждый механизм защиты — временный или обходимый.

Гранула score = 0.1. Пограничные значения всегда на сетке 0.1.

Удаление: score < −50.0.

3. Время
Тик = 1 запрос юзера = 1 вызов decay(). Пара диалога ≈ тик (пара появляется только при успешном ответе).
Старт агента: −2.0 всей памяти, кроме TGS. Обоснование: агент не работал — факты «остыли» без практики; TGS — сверхнагретая рабочая зона, стартовый штраф не заслужила. Реализация: cold_start_penalty(), вызов в initialize().
После стартового −2 записи распределяются по классам: no_compress со score ≤ 0.5 → ловушка/миграция (§5); unprotected со score ≤ 5.0 → очередь дистилляции (§5). Каждый класс — в свой коридор.
3.1. Персистентный счётчик тиков
data/meta.json: {"total_ticks": N}. Инкремент при каждом decay(), читается при старте. Использование: страховка user_fact (§8), enforcing лимита нагрева (§4), отладка остывания. Не сбрасывается рестартом.

Правило лестницы промоции: в HOT нагрев не капится. Нагрев, выводящий HOT-запись выше 49.9, — триггер промоции в TGS; вход со score = min(расчётный, 60.0). В TGS нагрев капится 60.0.

Глобальный потолок нагрева = 60.0 (в коде был 100.0 — дефект реализации ADR-012).
Enforcing «один нагрев за тик»: на записи хранится last_heat_tick. Нагрев при last_heat_tick == total_ticks не меняет score, а обновляет только updated_at. Revival считается нагревом тика. Побочный эффект (осознанный): recall + remember в одном запросе → второй нагрев (в т.ч. дедупный +10) деградирует до обновления updated_at; факт при этом найден и освежён.
updated_at обновляется любой операцией нагрева — LRU меряет «когда использовали», не «когда писали».
4.1. Остывание (decay)

Активный режим: не было вызовов recall_memory за последние 10 запросов. Адаптивная формула старого кода (max(0.01, 0.1 − n×0.0003)) отменена.

decay() не уважает no_compress — флаг защищает только от дистилляции (§5).

5. Два пути вниз из HOT (два коридора)
Защита no_compress — только от дистилляции. Не защищает: от decay, от forget, от forget_all (после истечения страховки §8), от стартового −2.

Класс записи
Триггер
Действие
Без no_compress	score ≤ 5.0 (нижней границы нет)	Очередь дистилляции: compress_cycle — LLM-саммари, вход в COLD со score = −5.0 (фикс)
Под no_compress	ловушка: score ≤ 0.5 после любой понижающей операции	миграция as-is: value сохраняется целиком, без LLM; на финише миграционный штраф −0.7; вход в COLD с получившимся score

Коридор дистилляции открыт вниз. Рестарт не может выкинуть запись из-под компрессии: −3.5 − 2 = −5.5 → всё ещё ≤ 5.0 → в очереди. Зомби-записи невозможны.
Событийная модель: по итогам тика запись, впервые опустившаяся ≤ 5.0, немедленно попадает в очередь компрессии (фоновое исполнение). Период цикла — не параметр.
Пере-валидация очереди при исполнении: запись со score > 5.0 или no_compress = True на момент исполнения — вычёркивается без дистилляции.
Ловушка ≤ 0.5 применяется к результату вычета немедленно, до сохранения. Арифметический результат может лежать вне HOT-пула — это transition value, не состояние. Сохранённых внепуловых состояний не существует, кроме записей в очереди дистилляции (вход в COLD всё равно фиксирован −5.0).
COLD-запись естественной миграции хранит value полностью; поиск — по value ИЛИ summary во всех зонах.
Приоритет: дистилляция > миграция; миграция — путь для no_compress-записей.
6. Revival (воскрешение из COLD)
Триггеры: recall(key), remember(key, ...), remember_user_fact(...) — по общим правилам операций.

Вход в HOT: score = max(текущий + N, 2.0), где N — прирост операции (+5 recall, +10 remember); no_compress = True; changed_since_revival = False. Повторный revival: флаг ставится заново, счётчик изменения сбрасывается.

Снятие флага — при операции нагрева, при обоих условиях: score ≥ 8.0 И changed_since_revival = True (факт был изменён/дополнен). Единственный способ снятия.

Value у revived-дистиллированной записи: value не восстанавливается, содержимое — summary (поиск в HOT покрывает summary, §9). remember восстанавливает value. Обратная миграция сохраняет пару value=None/summary as-is. Следствие: неизменённая дистиллированная запись гуляет COLD→HOT→COLD без повторной дистилляции текста — замкнутый контур без деградации.

Эмерджентный случай: revival через remember из глубокого COLD даёт вход max(−5+10, 2) = 5.0 < 8.0 — флаг держится (изменение зафиксировано, скор мал) и снимается при первом же касании (recall → 10 ≥ 8 при changed=True). Саморазрешается за одно касание — задокументировано.

Траектория «разведка/прописка» (базовый режим, все числа проверяемы):

text

COLD(−5.0) → recall: max(−5+5, 2.0) = 2.0, no_compress
тики: 1.7 → 1.4 → 1.1 → 0.8 → 0.5 → ловушка
миграция: 0.5 − 0.7 = −0.2 → COLD(−0.2)          [одно касание = ~5 тиков]
COLD(−0.2) → ещё recall: max(−0.2+5, 2.0) = 4.8   [прописка]
COLD(−0.2) → remember: max(−0.2+10, 2.0) = 9.8, изменён → флаг снят
Следствие (осознанное): факт, который только перечитывают, но не изменяют, не дистиллируется — сжимать нечего, саммари актуально. При частых касаниях факт поднимается по лестнице промоции до TGS (рабочий факт и есть рабочий); при затухании касаний — честно уезжает в COLD.

7. TGS: рабочий кэш с TTL
Лимит 10 записей. Переполнение: вытеснение по минимальному updated_at (LRU) → HOT со score = 40, shield = False (иммунитет от стартового −2 — свойство членства в TGS).
no_compress переживает промоцию и eviction (снятие — только по §6): неизменённый факт, вернувшийся из TGS, по-прежнему не имеет «чего дистиллировать»; изменение в TGS через remember снимает флаг автоматически.
Decay: −0.1/тик (оба режима). Нагрев: +5 при каждом использовании (recall/heat_facts), кап 60. Экономика: recall из середины диапазона покупает ~50 тиков жизни; не используемый ~100 тиков факт опускается ниже 50.0 → миграция в HOT(40) → общие правила → COLD → удаление.
Стартовый −2 на TGS не действует (§3).
Промоция: HOT-запись, нагретая выше 49.9 (§4).
8. user_fact
Ключ user_fact:*, вход: score = 40, uuid-ключ.
Страховка от forget_all: 10 тиков с момента записи (сравнение created_tick с персистентным total_ticks). Threat model: защита от случайного подтверждения тотальной ротации. Амнистия защищает свежие факты от попадания под случайную ротацию; записи старше окна считаются подтверждённо удаляемыми — ротация исполняется по ним.
Поведение в окне: ротация исполняется по всем записям вне окна; свежие факты амнистируются; агент отвечает с числами («очищено N, сохранено M свежих фактов, повторите после тика X»). Не распространяется на точечный забудь объект — юзер может осознанно удалить ошибочный факт в любой момент.
Иммунитетов к decay нет. Смертность — общая.
9. Поиск
recall_memory(query) ищет во всех трёх зонах (TGS включительно): по value ИЛИ summary. Зоны-призраки недопустимы: тулза поиска — единственный канал доставки фактов.
Дедупликация фактов автоматически видит TGS (тот же поиск).
build_context() удаляется (мёртвый код; инжект-канал не существует — проверено grep).
