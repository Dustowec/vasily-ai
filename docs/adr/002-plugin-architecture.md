# ADR-002: Модульная архитектура через Plugin Manager

## Статус
Принято

## Контекст
Исходный код агента — монолит на 600+ строк, где всё перемешано:
- Парсинг Danbooru
- Веб-поиск через SearXNG
- Генерация артов
- Работа с памятью
- Логирование

Проблемы монолита:
1. Сложно добавлять новые функции (риск сломать существующие)
2. Невозможно тестировать компоненты изолированно
3. Код становится "спагетти" — всё зависит от всего
4. Нельзя переиспользовать модули в других проектах

## Решение
Разбить монолит на независимые модули через паттерн **Plugin Manager**.

**Архитектура:**
\\\
vasily_ai/
├── core/              # Ядро агента (AgentCore, PluginRegistry)
├── plugins/           # Независимые инструменты
│   ├── danbooru/      # Плагин для парсинга Danbooru
│   ├── web_search/    # Плагин для веб-поиска
│   ├── art_generator/ # Плагин для генерации артов
│   └── memory/        # Плагин для работы с памятью
├── integrations/      # Внешние сервисы (LLM, API)
└── interfaces/        # UI (CLI, Web, Telegram)
\\\

**Базовый интерфейс плагина:**
\\\python
from abc import ABC, abstractmethod

class BaseTool(ABC):
    name: str
    description: str

    @abstractmethod
    async def execute(self, **kwargs) -> dict:
        pass

    def get_schema(self) -> dict:
        # JSON-схема для LLM, чтобы она знала, что умеет плагин
        return {...}
\\\

**Автосканирование плагинов:**
\\\python
# PluginRegistry автоматически находит все плагины в папке plugins/
registry.discover_plugins("vasily_ai.plugins")
\\\

## Последствия

### Положительные:
- ✅ Можно добавлять новые функции, создавая новый файл в plugins/
- ✅ Каждый плагин можно тестировать изолированно
- ✅ Плагины можно переиспользовать в других проектах
- ✅ LLM получает JSON-схему всех доступных инструментов
- ✅ Параллельная разработка (разные люди работают над разными плагинами)

### Отрицательные:
- ❌ Больше файлов и папок (сложнее навигация)
- ❌ Нужна дисциплина (плагины должны следовать интерфейсу)
- ❌ Overhead на регистрацию и вызов плагинов (минимальный)

### Альтернативы, которые рассматривали:
1. **Простое разделение на модули** — отклонено, потому что нет единого интерфейса
2. **Django-style apps** — отклонено, потому что избыточно для агента
3. **Microservices** — отклонено, потому что слишком сложно для локального приложения
