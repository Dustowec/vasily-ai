ADR-006: Отказ от внедрения шифрования данных в Фазе 4
Статус: ПРИНЯТО

Дата: 2026-08-10

Автор: Команда разработки Vasily AI

Контекст
В первоначальном плане проекта (см. РОАДМАП.txt) Фаза 4 предусматривала внедрение комплексной системы шифрования данных:

CryptoProvider (Fernet + PBKDF2)

KEK/DEK схема

Ротация пароля без потери данных

Шифрование резервных копий

Аутентификация CLI пользователя

В ходе анализа текущего состояния проекта и зрелости команды разработки возникли вопросы о целесообразности реализации данного функционала на текущем этапе.

Решение
Отложить внедрение всех компонентов шифрования данных (Шаги 4.1–4.4) на неопределенный срок. В рамках Фазы 4 реализовать только минимальную аутентификацию CLI (Шаг 4.5) как опциональную функцию.

Обоснование
1. Модель угроз не соответствует текущему сценарию использования
Василий AI является локальным агентом, работающим на персональной машине разработчика. Агент:

Не принимает внешние сетевые подключения

Не содержит многопользовательскую модель доступа

Не хранит критически важные персональные данные пользователей

Взаимодействует только с локальным Ollama и настроенными внешними API (SearXNG, Danbooru)

При такой модели угрозы:

Перехват данных в транзите: отсутствует (все локально)

Несанкционированный доступ к хранимым данным: требует физического доступа к машине, при котором шифрование бессмысленно

Атаки через API: отсутствуют (нет сетевых эндпоинтов)

2. Соотношение сложность/польза критически низкое
Внедрение шифрования требует:

Сложной архитектуры управления ключами (KEK/DEK)

Механизмов безопасной ротации без потери данных

Тщательного тестирования криптографических операций

Постоянного контроля за состоянием ключей

Польза при этом:

Защита данных от локального доступа (бессмысленно при наличии физического доступа)

Формальное соответствие "безопасности" без реальной необходимости

3. Риски внедрения на раннем этапе превышают пользу
Основные риски:

Потеря данных: Ошибка в управлении ключами приведет к полной потере доступа к данным агента (журналы, память, настройки)

Сложность отладки: Проблемы шифрования маскируют реальные ошибки в логике агента

Увеличение времени разработки: Добавляет 4-5 шагов, которые могут затянуть проект на недели

Демотивация команды: Новый разработчик (опыт: 5 дней в IT) может увязнуть в сложностях криптографии

4. Альтернативные приоритеты имеют большую ценность
Текущий фокус должен быть направлен на:

Стабилизацию существующей функциональности (ReAct, плагины, память)

Развитие пользовательского опыта (Web UI, MCP)

Улучшение качества кода и тестового покрытия

5. Безопасность ≠ шифрование
Для локального агента базовые меры безопасности могут включать:

Аутентификация CLI: Простой вход по паролю (может быть добавлена)

Санация логов: Уже реализована (ТЗ-016.5)

SSRF защита: Уже реализована (P3-2)

Проверка входящих данных: Уже реализована (ТЗ-017.6)

Эти меры покрывают 90% реальных угроз без сложного шифрования.

Последствия
Положительные:
Ускорение выхода продукта на стадию "рабочий прототип"

Снижение когнитивной нагрузки на разработчика

Уменьшение технического долга (не вводится сложная архитектура без необходимости)

Возможность сосредоточиться на функциональности, имеющей реальную ценность

Отрицательные:
Данные агента не будут зашифрованы на диске

Нет готовой инфраструктуры для будущего многопользовательского режима

Компенсирующие меры:
Документировано решение и причины (данный ADR)

В будущем, при изменении модели угроз, вопрос может быть пересмотрен

Аутентификация CLI может быть добавлена как опциональная функция с минимальными затратами

Альтернативы, которые были рассмотрены
Альтернатива	Решение	Причина отклонения
Полная реализация Фазы 4	Отклонена	Несоразмерная сложность для текущего этапа
Реализация только аутентификации	Принята	Минимальная сложность, реальная польза
Использование готового решения (Vault)	Отклонена	Избыточно для локального агента
Шифрование только резервных копий	Отложена	Требует реализации KEK/DEK, отложена до появления реальной необходимости
Связанные артефакты
РОАДМАП.txt — оригинальный план Фазы 4

HANDOFF.md — текущий контекст проекта

ADR-005-internal-timers.md — прецедент упрощения архитектуры

ТЗ-016.5 — санация логов (частичная безопасность уже реализована)

P3-2 — SSRF защита (частичная безопасность уже реализована)

Решение
Фаза 4 сокращается до опциональной аутентификации CLI. Шифрование данных переносится в Backlog до появления реальной необходимости.
