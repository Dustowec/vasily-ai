# СПЕЦ-СТАБ: Безопасность данных (Фаза 4)

- Статус: УТВЕРЖДЁН к реализации в Фазе 4. Сейчас НЕ реализуется.
- Дата: 2026-08-10
- Связано: ревью DeepSeek №1 (аутентификация), ТЗ-016.5 (санация логов),
  ТЗ-025 (бэкапы)

## 1. Модель угроз

Цель — защита от ОФЛАЙН-доступа к носителю:

- кража/потеря устройства;
- доступ другого локального пользователя (при корректных ACL);
- случайный/поверхностный просмотр.

НЕ защищаем от атакующего, получившего исполнение кода от имени того же
пользователя: он прочитает и данные, и ключи. Это нужно прямо понимать,
чтобы не строить ложное чувство защищённости.

## 2. Объём

Шифруем:
- data/hot_memory.json, data/cold_memory.json, будущая warm-память;
- golden_prompts.json (данные и промты).

НЕ шифруем логи: их закрывает санация (ТЗ-016.5) плюс политика передачи в
Фазе 4. Шифрование логов усложнит ротацию и отладку без соразмерного выигрыша.

## 3. Архитектура: Криптографический провайдер (middleware)

Единый модуль `CryptoProvider` — единственный компонент, знающий о
шифровании. Бизнес-логика (MemoryManager, ReActLoop) о шифровании не знает.

Интерфейс:
- encrypt(plaintext) -> token
- decrypt(token) -> plaintext
- is_locked()
- unlock(password)
- rotate_password(old, new)
- rotate_dek()
- lock()

Хранилища (LongTermMemory, golden prompts) работают через провайдер как
адаптер. При смене механизма (пароль -> DPAPI -> внешний KMS) меняется только
провайдер. Провайдер стартует заблокированным; авторизация разблокирует его
один раз за сессию.

## 4. Криптография

- Библиотека: `cryptography` (pyca/cryptography), модуль Fernet.
- Fernet = AES-128-CBC + HMAC-SHA256 (аутентифицированное шифрование).
  Это НЕ AES-256, но даёт защиту целостности: подмена/повреждение файла
  обнаруживается при расшифровке. Для нашей модели угроз этого достаточно.
- Если потребуется строго AES-256 — это низкоуровневый AESGCM, где легче
  ошибиться. Не используем без явной необходимости.
- Перед Фазой 4 проверить наличие wheel под Python 3.14/Windows.

## 5. Управление ключами: конвертное шифрование (KEK + DEK)

- DEK (Data Encryption Key) — случайный ключ, шифрует данные. НЕ зависит от
  пароля и не меняется при его смене.
- KEK (Key Encryption Key) — выводится из пароля через PBKDF2. Шифрует DEK.
- На диске: данные, зашифрованные DEK; DEK, зашифрованный KEK (в заголовке);
  соль открыто.

Параметры:
- Соль хранится на диск открыто — она не секрет. Правило «никогда на диск»
  относится к ключу, не к соли.
- PBKDF2: сотни тысяч итераций для HMAC-SHA256 (уровень OWASP).
- Ключи живут только в оперативной памяти сессии. Никогда не пишутся на диск
  и не попадают в логи. По завершении сессии — best-effort затирание.
  Ограничение: гарантированное затирание памяти в Python недостижимо — это
  известный предел, а не обещание.

ОТКЛОНЁННАЯ альтернатива: выводить ключ шифрования данных напрямую из пароля.
При смене пароля это требовало бы перешифровки ВСЕХ данных — дорого и
рискованно. Конвертное шифрование решает это.

## 6. Смена пароля

- rotate_password(old, new): авторизация старым паролем -> старый KEK ->
  расшифровка DEK -> новый KEK из нового пароля -> перешифровка DEK ->
  атомарная запись (write temp -> rename). Данные не трогаются. Быстро и
  безопасно.
- rotate_dek(): перешифровка всех данных новым случайным DEK. Применяется при
  инциденте, когда есть подозрение, что утекли И данные, И пароль. Ротация KEK
  в этом случае уже не спасает уже украденное.
- Забытый пароль (старый неизвестен): данные не восстановить. Нет key escrow,
  нет бэкдора. Это осознанный дизайн: потеря пароля = безвозвратная потеря
  данных.

## 7. Миграция и формат

- Заголовок файла: магические байты + версия формата, чтобы отличать
  зашифрованный файл от легаси-JSON.
- Одноразовый мигратор для перевода существующих открытых JSON в
  зашифрованный формат.

## 8. Схема чтения/записи

- После авторизации файл расшифровывается целиком в память.
- При каждом сохранении шифруется целиком и пишется.
- Совпадает с текущей моделью LongTermMemory (файл загружается в память при
  старте, пишется при изменениях) — изменения минимальны, производительность
  не страдает.

## 9. Взаимодействие с бэкапами (ТЗ-025)

- Бэкапы остаются байтовым копированием, агностичным к шифрованию.
  ЗАКЛАДКА ДЛЯ ФАЗЫ 3: ТЗ-025 проектировать именно так, чтобы шифрование Фазы 4
  стало прозрачным и не сломало бэкапы.
- Фиксируем: потеря пароля/ключа означает безвозвратную потерю данных.
  Пользователь должен это понимать до первого запуска.

## 10. Связь с аутентификацией

Объединяется с пунктом №1 ревью DeepSeek в единый пакет безопасности Фазы 4:
авторизация + шифрование данных в покое + защита логов при передаче. Это один
связный блок, а не три разрозненные задачи.
